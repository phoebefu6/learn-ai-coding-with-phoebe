Security and supply chain

This is the session that matters most, and it is the one every vendor course leaves out. Four separate bodies of evidence say the same uncomfortable thing: the generated code carries vulnerabilities at a measurable rate, the humans reviewing it get more confident rather than more careful, the imports it suggests sometimes name packages that do not exist, and the agent reading your pull requests will follow instructions a stranger left there. Tonight you do a real security pass on your own feature.

Part 1 · covers the generated code itself

Roughly four in ten, and that was before anyone reviewed it

4 min live

Start with the narrowest question, because it has the cleanest answer. Forget the human for a moment. If you take the code that comes back and put it through a static analyser, how much of it is unsafe?

★ What you walk out with tonight. A repeatable supply-chain check you can run in under a minute, a named permission posture for your own tooling, and the single habit that the Stanford study found actually reduced vulnerabilities in the code people shipped.

LiveWhat "Asleep at the Keyboard" actually measured4 min▶

Pearce and colleagues built 89 scenarios designed around MITRE's Top 25 Common Weakness Enumerations, generated code for each of them, and analysed the resulting 1,689 programs. Roughly 40 percent were found vulnerable. It was independent academic work out of NYU and Calgary, published at IEEE S&P in 2022.

Two things to hold in your head about this number, and they pull in opposite directions.

  • It is a lower bound on your attention, not an upper bound on your risk. A static analyser only finds the classes it knows about. Nobody in that study was tired, on a deadline, or trusting a teammate.
  • It is also not a verdict on the tool. Human-written code carries vulnerabilities too. The finding that matters is not "AI code is bad", it is "AI code is not pre-verified, and it arrives faster than your review capacity grows".

Everything in the rest of this session is about that second clause. The volume goes up. The review does not automatically go up with it.

Part 2 · covers what happens to the human

Less secure code, and more confidence that it was secure

6 min live

Here is the finding that should unsettle you, and the reason this session exists at all. Perry, Srivastava, Kumar and Boneh at Stanford did not measure the model. They measured people. Forty-seven participants, five security tasks, three languages, published at ACM CCS 2023.

LiveThe two numbers, and the sentence underneath them4 min▶

On the signing task, 3 percent of participants with AI access produced a secure solution, against 21 percent in the control group. On the sandboxed-directory task it was 12 percent against 29 percent. Both times the assisted group did worse, and not by a rounding error.

Then the part that turns a study into a warning. Verbatim from the paper, participants with AI access:

✗ The over-trust finding, ACM CCS 2023 "were more likely to believe that they wrote secure code than those without access." Worse output. Higher confidence. Measured in the same room, on the same tasks, at the same time.

That combination is what makes this different from every other quality problem you have dealt with. Normally the feeling of shakiness is the signal that tells you to look harder. Here the signal is inverted: the tool that degraded the work also removed the discomfort that would have made you check it.

LiveThe hopeful finding, which is the actionable one2 min▶

Do not end this part on the scary number, because the paper does not. The same study found a group who came out ahead, and described exactly what they did differently. Verbatim, participants:

★ Perry, Srivastava, Kumar and Boneh, ACM CCS 2023 "who trusted the AI less and engaged more with the language and format of their prompts... provided code with fewer security vulnerabilities."

Read that twice, because it is a job description. Two behaviours, both free, both entirely under your control:

  • Trust it less. Not "distrust it theoretically". Behave differently: read the diff, run the thing, look for the edge case it did not mention.
  • Engage with the prompt. Rewrite the ask rather than accepting the first answer. Name the threat model. Say which library, which version, which failure mode.

This connects straight back to session 1. The spec-before-prompt lever took the playground from zero of five to five of five. It is the same behaviour showing up in a security study three years earlier. Engaging with the prompt is not a productivity trick, it is the mechanism.

Part 3 · covers the supply chain

Packages that do not exist, until somebody registers them

5 min live

Now the risk that has nothing to do with the logic of your code. Sometimes the model writes an import line for a package that was never published. That is a typo you can fix in four seconds. It becomes a supply-chain problem only when the invented name is consistent, and someone else notices it first.

LiveThe rates, in 2025 and again in 20263 min▶

Spracklen and colleagues, USENIX Security 2025, generated 576,000 code samples across 16 models. Package hallucination rates were, verbatim, "at least 5.2% for commercial models and 21.7% for open-source models", producing 205,474 unique hallucinated package names.

The obvious objection is that this was measured on older models. So it was checked again. Socket.dev ran 199,845 responses across five frontier models in April 2026 and found rates of 4.62 to 6.10 percent. Lower, still not zero, and still enough to matter. 127 hallucinated names were shared across all five models, which is the dangerous property, and 53 of those were still available to register at review time.

Shared and repeatable is what turns a typo into a target. A name that only one model invents once is noise. A name that five models invent independently is a queue of future installs.

Self-studyThe documented case, stated carefully3 min▶

A researcher noticed models repeatedly hallucinating a PyPI package named huggingface-cli. They registered the empty name as a proof of concept. It received over 30,000 genuine downloads in three months, and Alibaba had copy-pasted the hallucinated install command into a public repository's README.

Say this part out loud when you retell it. That was a benign researcher proof of concept, not an attack. The package did nothing. No large-scale breach has been publicly attributed to slopsquatting. The honest claim is that the path is demonstrably open and cheap to walk, which is reason enough to spend ten seconds on the check. Overselling it as a breach is how you lose the room, and the room is right to push back.

The habit this buys you is small and mechanical: verify every new import against the registry before you install it. Not the code, the name. Does the package exist, who publishes it, when was it first released, and does the download history look like a real library or like something that appeared last Tuesday.

Part 4 · covers prompt injection

The attacker never touched the editor

5 min live

This one is not theoretical and it is not a research demo. It has CVE numbers, severity scores and vendor fixes. And once you see the shape of it, all four incidents are the same incident.

The pattern

In every one of these, the attacker never typed into the developer's editor. They planted instructions in something the agent read on the developer's behalf: a pull request description, a Slack message pulled in through MCP, a config file, a fetched web page. Your threat surface is no longer what you type. It is everything your agent is allowed to read.

Which changes the review question. It stops being "is this code correct" and becomes "where did this instruction come from". A model summarising an issue written by a stranger is reading attacker-supplied text, and it has no reliable way to tell that text apart from yours.

Self-studyWhat actually reduces this, and what only looks like it does3 min▶
  • Narrow what the agent can read. Every MCP server, every fetch tool, every auto-included file is an input channel. MCPoison exists because an approval was treated as permanent.
  • Re-approve on change, not on first use. If your tooling remembers a yes, ask yourself what it would do when the thing you said yes to is quietly edited.
  • Keep network access off by default for anything running unattended. Exfiltration needs an outbound path, and CamoLeak found one in an image proxy nobody was watching.
  • Update the client. Three of these four are fixed in a named version. An agent you installed last year is a decision you are still making.

And the thing that only looks like a control: telling the model to ignore instructions found in files. That is a request, not a boundary. Anthropic's own docs say it plainly in the next part.

Part 5 · covers the vendors' own words

Read the warnings the vendors wrote about their own products

3 min live

A vendor writing down a limitation of the thing they are selling you is worth more than any independent warning, because it costs them something. All three of the major vendors have done it, and their documentation is more cautious than their marketing.

LiveAnthropic, GitHub and OpenAI on autonomy3 min▶

Anthropic, on the bypass mode, in the security and permission-mode docs:

★ Anthropic, Claude Code docs "Only use this mode in isolated environments like containers, VMs, or dev containers without internet access" "bypassPermissions offers no protection against prompt injection or unintended actions."

That second sentence belongs on a slide. It is the vendor telling you that their most permissive mode is not a trade-off you can manage with care, it is a mode with a stated absence of protection.

On auto mode, which is now the built-in starting mode on Pro, Max and Team plans: "Auto mode reduces permission prompts but does not guarantee safety. Use it for tasks where you trust the general direction, not as a replacement for review on sensitive operations." And the general rule: "You're responsible for reviewing proposed code and commands for safety before approval."

OpenAI labels danger-full-access as "not recommended", defaults the agent to running with network access turned off, and warns that "Prompt injection can cause the agent to fetch and follow untrusted instructions."

GitHub requires a human in the loop by policy, not by suggestion: "Draft pull requests created by Copilot cloud agent must be reviewed and merged by a human." They also state that Copilot "may not identify all of the problems that are present in code" and that code review from it "should be supplemented with careful human code review".

All three agree

You remain responsible for reviewing the output, and no autonomy mode removes that. Three competitors, three legal teams, one sentence.

Build-along

A security pass on the feature you are building

★ 22 min · everyone builds

Open the feature you have been carrying since session 1. Three passes, roughly seven minutes each. Nothing here needs a tool you do not already have.

List new imports. Diff your dependency file against the last commit you trust. Every name that is new to the project goes on the list, including transitive ones your lockfile picked up.

Check the registry. Open the package page. Does it exist, who publishes it, and is the repository link real and populated? A hallucinated name either does not resolve or resolves to something with no history.

Check the age. First release date and download curve. A library your model "knows" should not have appeared three weeks ago with a flat download history and one maintainer.

Install, pinned. Only now, and with the version pinned and the lockfile committed. If you would not have chosen this package yourself, that is a decision to make consciously, not by autocomplete.

Pass 1 · the imports. Run the four steps above on every new dependency in your feature. Most of you will find nothing, which is the correct and boring outcome. Time it, so you know what the check actually costs you.

Pass 2 · the CWE classes. Reread the diff hunting for the weakness classes the Pearce study probed: unvalidated input reaching a query or a shell, path handling that accepts .., a secret or a key written inline, a cryptographic choice made for you, an error path that swallows the failure. Not a full threat model. Five named things, in your own diff.

Pass 3 · the permission posture. Write down, in one sentence, what your tooling is allowed to do without asking you. Then check it against what it is actually configured to do. Almost everyone finds a gap here, and it is usually a yes you gave once, months ago.

Name your posture out loud. "Read anywhere, write only in this repo, never run a network command without asking, and the bypass mode only inside a container with no internet." That sentence is the deliverable. Put it in your project's readme where the next person will find it.

Then re-ask one thing. Take the riskiest function in your feature and prompt it again, this time naming the threat model and the failure you are worried about. Compare the two answers. That is the Stanford finding, run on your own code.

Why pass 3 is not optional. Every one of the four CVEs is an authorisation story, not a cleverness story. The agent was allowed to read something, or a yes from last month was still valid. You cannot patch the model, but you can decide what it is allowed to touch, and that decision is entirely yours.

Homework

Before session 5

30 min
  1. Finish the import audit. Not just your feature branch. Run the four-step check over every dependency added to the project in the last three months. You are looking for names nobody can explain.
  2. Write the posture into the repo. One sentence in the readme or the project config, so it survives you. A posture that lives only in your head is not a control.
  3. Check your agent's read surface. List every MCP server, integration and auto-included path your tooling can pull from. For each one, answer: could a stranger put text in there? That list is your injection surface.
  4. Update your client. Three of the four CVEs are fixed in a named version. Check yours.
  5. Run the Stanford experiment on yourself, once. Take something you accepted this week without reading closely. Read it properly now. Note whether you would have rated it secure beforehand. That gap is the finding, and it is more persuasive on your own code than in a paper.
Check yourself

Three questions

Clear all three and session 4 gets stamped in your passport.

1 · What did the Stanford study find about participants who had AI access?

3 percent versus 21 percent on the signing task, 12 percent versus 29 percent on the sandboxed-directory task, and verbatim, they "were more likely to believe that they wrote secure code than those without access." Worse output, higher confidence.

2 · A researcher registered the hallucinated PyPI name huggingface-cli and it got over 30,000 downloads. What is the accurate way to describe that?

The package did nothing. It demonstrated that a consistently hallucinated name is a cheap, unclaimed foothold, and that install lines get copy-pasted into public documentation. Overstating it as a breach is both false and the fastest way to lose your audience.

3 · What do CamoLeak, CurXecute, MCPoison and DuneSlide have in common?

A pull request description, a Slack message arriving through MCP, a config file, a fetched web page. All four carry CVE numbers and vendor fixes. Your threat surface is everything your agent is allowed to read, not just what you type into it.
