Part 1 · covers DORA 2025

Ninety percent use it, thirty percent do not trust it

7 min live

You have a real feature, written over five sessions, sitting on a branch. The only question left is the one the course was built around: does merging it make your codebase better or worse? That question has a team-scale answer, and DORA's 2025 report, "State of AI-assisted Software Development", is where it lives. Roughly 5,000 professionals, and three numbers that are the spine of this session.

🎫 Clear all three quiz questions to stamp your final passport slot Live = presented in the 45 minutes Self-study = the full depth, after class
LiveThe pivot from 2024, and the sentence underneath it6 min▶

The 2025 report changed its own position on throughput. In DORA's words, "we observe a positive relationship between AI adoption on both software delivery throughput and product performance". That is new, and it is good news. The same sentence keeps going: "However, AI adoption does continue to have a negative relationship with software delivery stability."

★ DORA 2025, the mechanism, verbatim "AI accelerates software development, but that acceleration can expose weaknesses downstream. Without robust control systems, like strong automated testing, mature version control practices, and fast feedback loops, an increase in change volume leads to instability."

Read that as an engineering statement rather than a caution. It names the input, the failure mode, and the three things that prevent it. That is a specification for what you build tonight.

"AI doesn't fix a team; it amplifies what's already there." DORA, 2025. This explains every contradiction in the course at once. A team with a suite that asserts, small diffs and fast feedback gets amplified into shipping more. A team without those gets amplified into more incidents. Same tool, same prompts, opposite outcome. It also makes "should we adopt AI" the wrong question for a lead to ask. The honest version is what is already true about how we ship, and do we want more of it?

Part 2 · covers the control system

The control system is the deliverable

6 min live

DORA named four things: automated testing, version control practices, fast feedback, and the change volume sitting on top of them. Here is what each one means when you are the one merging.

LiveTests that assert, not tests that merely execute4 min▶

Session 1 ended with a playground that scored five out of five while shipping four real defects. Its final form: a green suite proves the tests ran, not that the code is right. Coverage measures execution. Assertion measures belief. The failure mode is documented: tests generated after faulty code detect roughly 14 percent of faults against roughly 25 percent for tests generated independently, because "incorrect implementations and tests are mutually consistent, masking defects rather than revealing them". The test agreed with the bug.

Go deeper

This is a discipline with its own course: learn-ai-qa-with-phoebe. It exists because the check you need here cannot be done by reading a pass count. Its playground scores the same shape of suite with real mutation testing, which is the only cheap way to find out whether your assertions would notice if the code were wrong. If you take one thing after tonight, take that.

Self-studyVersion control hygiene, and why it matters more now5 min▶
  • One logical change per commit. When change volume rises, bisect is the tool that saves you, and bisect is only as good as your commit boundaries.
  • A message that says why, not what. The diff already says what. In six months the only person who can reconstruct why is the one who wrote it down.
  • Branch, never straight to main. Especially when an agent is doing the typing, because the cost of a bad revert scales with volume.
  • Read the diff, not the summary of the diff. The summary was written by the same thing that wrote the code.
  • Four small pull requests beat one large one. A 1,400-line diff gets approved without being read. Four diffs of under 200 lines each get read end to end, on the same day, by the same reviewer.
✗ What skipping the read actually looks like git add . && git commit -m "fix stuff" && git push # 23 files staged, none of them opened
★ Ninety seconds that pay for themselves git diff --stat # is this diff smaller than ~200 lines? git diff # read it, every hunk, out loud if needed git diff --stat main... # what did the whole branch touch?
Part 3 · covers what the vendors themselves say

What you never hand over

5 min live

Not a policy handed down by a security team. A list you can defend, where every line is backed by the vendor's own documentation. When the company selling you the autonomy writes down its limits, that is worth more than any independent warning.

VendorWhat they wroteWhat it means for the list
Anthropic"You're responsible for reviewing proposed code and commands for safety before approval."No permission mode transfers that. Approval is an act you perform, not a setting you choose

None of these are about the model being weak. They are about where responsibility sits, which is why each one is a sentence you can quote in a review conversation without sounding like the person who is against progress.

The fifth item is not a security control. Four items on the list are about damage. The last one, the decision about what to build, belongs there because it fails the same way: quietly, and only visibly much later. An assistant will happily implement the feature you described. It has no way of knowing the feature should not exist, that the ticket describes a symptom rather than a cause, or that the right change is to delete something instead.

A cheap habit. Before you open the assistant, write one sentence naming who is worse off if this feature does not exist. If you cannot write it, you have found something more useful than a fast implementation.

Part 4 · covers licence and attribution

Licence and attribution, handled carefully

3 min live

Short section, handled precisely, because this is an area where confident claims outnumber verifiable ones. Only what the documentation actually says.

LiveWhat is documented, and where the documentation stops3 min▶
  • Copilot can be configured to block suggestions matching public code. It is a setting, and somebody has to have turned it on.
  • Code referencing shows the licence type of the matching code, or NOASSERTION when no licence is found. Treat NOASSERTION as unknown, not as free.
  • GitHub's own limitation note: the cloud agent "may generate code matching publicly available sources despite blocking policies". The vendor is telling you the filter is not a guarantee.

On the litigation. Doe v. GitHub is on appeal, with no ruling as of August 2026. That is the whole of what this course will say. Anyone offering you a confident prediction about the outcome, in either direction, is offering an opinion dressed as a fact, and you now know how to tell the difference.

One more thing this course will not do: quote a duplication-filter threshold in lexemes or characters. That number circulates widely and it is not on the documentation page, so it does not belong in your head as a fact.

Part 5 · covers reading the evidence

The honest closing on the evidence

4 min live

This course opened with the most-cited number in the field. It closes by returning to it, because what happened to that number is the most transferable thing here.

LiveWhat happened to the 19 percent, and what to do instead4 min▶

METR's 2025 trial measured 16 experienced developers across 246 tasks as 19 percent slower with AI, while those same developers believed they had been 20 percent faster. Then its own authors published a larger follow-up: 57 developers, 143 repositories, over 800 tasks. The returning developers came out at minus 18 percent with an interval of minus 38 to plus 9, the new recruits at minus 4 percent with an interval of minus 15 to plus 9. Both intervals cross zero, so neither result is distinguishable from no effect. They name severe selection bias as the cause and are redesigning the study.

★ METR, February 2026 "Based on conversations with study participants, we believe it is likely that developers are more sped up from AI tools now - in early 2026 - compared to our estimates from early 2025."

So the lesson to leave with is not a number. Every number in this course will move, and the good ones will move because their authors kept measuring. The lesson is a habit: measure your own throughput and your own rework, because published results describe somebody else's repository, tooling and task mix. If your own numbers disagree with a headline, your numbers win. That is not anti-science, it is exactly what the researchers keep telling you when they revise in public.

Build-along

Ship it, then run the control system over it

★ 22 min · everyone ships

Your feature has been in progress for five sessions. Tonight it merges, but only after it clears a gate. Walk the sequence first, then grade the thing you are about to put on main.

Diff. Read it hunk by hunk, not the summary of it. If the diff is too big to read, that is the finding: split it before you go any further.

Imports. Every new import gets resolved to a package that genuinely exists and that you meant to add. Hallucinated package names are a measured failure mode, not a rumour.

Tests. Open the test file and ask one question of each test: would this go red if the behaviour were wrong? A test that only executes the code is coverage theatre.

Secrets. Grep the whole branch for keys, tokens, connection strings and anything that looks like a credential. Generated config and fixture files are where these turn up.

Human. A person reviews it and a person merges it. GitHub requires exactly this for its own cloud agent's pull requests, and it is the right default for yours.

Finish the feature. Whatever is left, close it out now. Do not start anything new tonight, because the point of this session is the gate, not the code.

Split the branch if it needs splitting. Run git diff --stat main.... If the total is over roughly two hundred lines, find the natural seam and cut it into two pull requests. Reviewers read small diffs and skim large ones, and you already know which one you are.

Read the whole diff out loud. Genuinely out loud, or subvocalised. It is the cheapest known way to stop your eyes sliding over a plausible-looking line that does the wrong thing.

Check every new import. One at a time, against the registry. Not "it looks like a real package". Open it.

Interrogate one test. Take the test covering the riskiest behaviour, break the implementation deliberately, and confirm it turns red. If it stays green you have just learned the most valuable thing in this session.

Grade it, then merge it. Fill in the scorecard below honestly. Any row at zero is a reason to wait, not a reason to feel bad.

Every new import has been verified to be a package that really exists Opened in the registry, not recognised by eye. This is a measured failure mode with a name.
You read the diff line by line rather than skimming it Every hunk, including the parts that looked boring. The boring parts are where it hides.
The tests assert the behaviour rather than merely executing the code You broke something on purpose and watched a test go red. Green only proves the tests ran.
No secret, key or credential appears anywhere in what was generated You grepped the branch, including config, fixtures and anything written into a sample file.
A human reviewed it and a human merged it Not the same person who generated it, if you can help it. GitHub requires this for its own agent.
Homework

The last one: run your own measurement for a month

10 min a week

There is no session 7, so this homework has no deadline except the one you set. It is also the only part of the course that produces evidence about you rather than about somebody else.

  1. Track time to merge. For every change for four weeks: the moment you started, and the moment it landed on main including review and rework. A note in a text file is enough.
  2. Track rework rate. The share of those merged changes you had to go back and fix within a week. This is the number that catches speed which was not real.
  3. Compare against your session 1 baseline. You measured one honest task in week one. Four weeks against that is not a study, but it is yours, and it is more relevant to your decisions than any published figure in this course.
  4. Run the pre-merge sequence every single time, and then read the two numbers together. Faster with flat rework is a real win. Faster with rising rework is the DORA finding happening to you personally, and you now know exactly which part of the stack to go and fix.
