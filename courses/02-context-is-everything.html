Context is everything

The model is not clever and it is not lazy. It answers from what is in front of it, and nothing else. That single fact explains almost every bad output you have ever accepted, and it explains something less obvious too: a session that has been open all afternoon is not warmed up, it is degraded. Tonight you learn what the window actually holds, why it gets worse over hours, and the four mechanical moves that put the right things back in it.

Part 0

Where we left off

Last session you watched one lever take the playground from zero of five to five of five. That lever was the spec. Tonight is about the thing sitting next to the spec, which is everything else the model can see at the moment you ask.

🎫 Clear all three quiz questions to stamp your passport Live = presented in the 45 minutes Self-study = the full depth, after class

★ What you walk out with tonight. A written spec and a written context pack for your real feature, a habit of clearing between unrelated tasks, and a first-hand comparison of the same task run in a fresh session versus a stale one.

LiveTwo levers, and only one of them shows up in a test3 min▶

In session 1 the spec lever moved a number you could see. Zero of five to five of five, immediately, because naming the edge cases is the difference between deciding them yourself and letting the model decide them for you.

The context lever did something different. The score did not move at all. What moved was the amber note underneath it, the one saying the code had ignored the surrounding conventions and invented a third way of doing something the repo already does twice.

That is the honest shape of tonight's material. No test in your suite will ever turn red because a new function is a stylistic orphan. It passes, it merges, and the codebase quietly gets a little harder to read. Context is the lever with no scoreboard, which is exactly why it gets skipped.

Part 1 · covers what the model sees

What is actually in the window

6 min live

Think of it as a desk rather than a brain. Whatever you put on the desk gets used. Whatever you left in the drawer may as well not exist, no matter how obvious it is to you.

LiveThe spec, the surrounding code, the conventions4 min▶

The spec is what the thing must do, including the parts that are boring. Empty input. The boundary value. What happens on the error path. If you do not write those down, the model picks them, and it picks the most common pattern in its training rather than the one your system needs.

The surrounding code is the shape of the answer. Which helper already exists, how errors travel through this service, what a function in this file normally looks like. You know all of it and none of it is in the window unless you put it there.

The conventions are the rules nobody wrote down: this repo returns result objects rather than throwing, tests live next to the source, dates are always UTC at the boundary. These are the ones that produce the stylistic orphan.

Real world

An analyst asks for "a function to load the monthly file". What comes back reads pandas directly, hard-codes the path and raises on a missing file. All three are wrong for that team, and none of the three is a bug. Their loader module, their config object and their result-not-exception convention were all sitting in the drawer.

Self-studyWhy "it should have known" is the wrong instinct4 min▶

When a colleague joins your team you do not expect them to guess the conventions. You point them at three files and a wiki page. The assistant deserves less patience than the colleague and needs more of the same input, because it will never walk over and ask.

The useful reframe: every time you are annoyed at an output, ask what you would have had to hand a competent stranger for that answer to be obvious. That list is your context pack. It is usually shorter than you expect, and it is almost always the same list every time, which is why it belongs in a file rather than in your fingers.

Part 2 · covers the vendor's own mechanics

Why a long session quietly gets worse

7 min live

Most people treat a long session as an asset. It feels like the model has been learning about your problem all afternoon. Anthropic's own documentation describes something closer to the opposite, and it is worth reading in their words rather than mine.

LiveThree sentences from the docs that change how you work4 min▶

These are Anthropic's own words about their own product, which is why they carry weight. A vendor writing down a limitation is worth more than any warning from outside.

★ Anthropic, Claude Code cost documentation Claude Code "sends your full conversation with every request... so a one-line question in a session that has been open all day still draws usage for the whole conversation." Auto-compaction "summarizes conversation history when approaching context limits." "Use `/clear` to start fresh when switching to unrelated work. Stale context wastes tokens on every subsequent message."

Read them together and the mechanism is plain. Nothing is discarded as you work, so the bill grows with the length of the day rather than the size of the question. Then, when the window fills, the history is summarised, and a summary is lossy by design. The precise thing you agreed at 10am becomes a sentence about having agreed something.

Their own diagnosis of the teams who get a shocking invoice, verbatim, is that it "usually traces back to long sessions that were never cleared."

Self-studyWhat that costs, with the vendor's own benchmark3 min▶

The same documentation publishes a figure teams can plan against: "around $13 per developer per active day and $150-250 per developer per month". That is the benchmark to compare your own usage to, and it is the only cost number in this course that comes from the vendor rather than from a forum.

The habitWhat it does to the windowWhat it does to the bill

The part people miss. Cost and quality are the same problem here, not two problems. The stale history you are paying to resend is also the stale history the model is reading. You are being charged to be misled by this morning's abandoned approach.

Part 3 · covers the fixes

Four mechanical fixes

5 min live

None of these are clever. They are the equivalent of closing the tabs you are not using, and they work for the same unglamorous reason.

LiveThe four moves, in the order they pay off4 min▶

1. A project instructions file. One file at the root of the repo that states the conventions, the commands to run tests, the structure, and the things a newcomer always gets wrong. It loads with every session, so you stop paying to re-explain your codebase every morning.

2. Clear between unrelated tasks. Finished the bug, picking up the feature? Clear. The vendor's guidance is explicit and it is one keystroke.

3. Steer compaction with an explicit focus. If a summarisation is going to happen anyway, say what must survive it. Name the decision, the constraint and the file that matters, so the lossy step loses the right things.

4. Name the files. Do not hope it finds them. Pointing at three specific files is faster, cheaper and more accurate than asking it to search, and it also tells you something: if you cannot name the three files, you do not understand the task well enough to delegate it yet.

Self-studyWhat a small window does to a codebase over a year4 min▶

There is a consequence to all of this that shows up in the code itself rather than in the invoice. GitClear, analysing 211 million changed lines authored between 2020 and 2024, observed that the most popular assistant of 2024 was limited to roughly ten files fitting in its context window.

Follow that through. If the assistant can only see ten files, it cannot know that the helper you need already exists in the eleventh. So it writes a new one. That is not a flaw in the model's reasoning, it is arithmetic, and it is a direct mechanical driver of duplication.

Why this matters tonight rather than in session 3. Session 3 is about catching duplication in your diff. This is the cheaper version: pointing at the file that already contains the helper means it never gets written twice in the first place. Context work is duplication prevention.

Build-along

Your spec, your context pack, and one honest comparison

★ 22 min · everyone builds

Take the real feature you picked in session 1. By the end of these twenty-two minutes it has a written spec, a written context pack, and you have watched the same task run twice under different conditions.

Clear. New task, new window. If it does not touch the same files as the last thing, start clean.

Spec. What it must do, plus empty input, the boundary, and the error path. Written down, not held in your head.

Context. Name the three files. Name the convention it will otherwise break.

Ask. Now, and only now. The ask is the shortest part of the loop.

Check. Read the diff against the spec you just wrote. Session 3 is entirely about this step.

Minutes 1 to 6 · write the spec. Five bullets, no more. What it does, what it returns, what happens on empty input, what happens at the boundary, what happens when the dependency fails. If a bullet is hard to write, that is the bullet the model was going to guess.

Minutes 7 to 13 · write the context pack. Three files by path and one line each on why. The convention it must follow. The helper that already exists so it does not write a second one. Keep it as a note you can paste, because you will paste it many times.

Minutes 14 to 18 · run it stale. Use a session that has been open for a while on something else. Give it the bare ask, no spec, no context. Save what comes back without judging it yet.

Minutes 19 to 22 · run it fresh. Clear. Paste the spec, paste the context pack, then the same ask. Put the two outputs side by side and mark three concrete differences: a named edge case handled, a convention respected, a helper reused instead of reinvented.

The honest bit. Sometimes the stale run is fine. Note that too. The claim is not that context always changes the answer, it is that context is the only lever you control when the answer is wrong for reasons no test will report.

"Add a function to load the monthly usage file and return the totals."

Reads the file directly, hard-codes the path, raises on a missing file, and writes a parsing helper the repo already has in two other places.

"Add loadMonthlyUsage to reports/loaders.py. Follow the pattern in loaders.py and use the existing parse_row helper. Config comes from settings.py, never a literal path. Missing file returns a Result with an error, we do not raise across this boundary. Empty file returns zero totals, not None."

Uses the existing helper and config, returns the error rather than raising, and handles the empty file because you named it.

Homework

Before session 3

25 min
  1. Write the project instructions file. One file at the repo root. Conventions, test command, structure, and the three things newcomers always get wrong. Twenty lines is plenty and it pays for itself in a week.
  2. Clear between tasks for one week. Every time you switch to unrelated work, clear. Note the two or three moments where it felt wasteful, because those are the moments worth discussing in session 3.
  3. Catch one compaction. Next time a long session summarises itself, read what survived and write down one thing that did not. That is the concrete cost of a lossy step.
  4. Ship the next slice of your feature using the Clear, Spec, Context, Ask, Check loop. Bring the diff to session 3, because that diff is what session 3 reviews.
  5. Optional. Compare your own usage against the vendor's published benchmark of around $13 per developer per active day. If you are far above it, the first thing to check is session length, not model choice.

Three questions

Clear all three and session 2 gets stamped in your passport.

1 · Why does a session that has been open all day get more expensive and less reliable at the same time?

Anthropic's docs say Claude Code "sends your full conversation with every request", so a one-line question in an all-day session still draws usage for the whole conversation. Auto-compaction then "summarizes conversation history when approaching context limits", which is lossy by design.

2 · In session 1's playground, switching on "give it the surrounding code" did not move the score at all. What did it change?

The score stayed at five of five and the amber convention warning cleared. That is the whole lesson: the context lever has no scoreboard, so it gets skipped, and the cost lands on the next person to read the file.

3 · You finish a bug fix and pick up an unrelated feature in the same session. What does the vendor's own guidance say to do?
